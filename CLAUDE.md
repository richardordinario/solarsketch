# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

The product spec is `docs/prd.md` (PRD v1.1, MVP, frontend-only revision). The app is **frontend-only by design**: no backend, no accounts, no login and no Dashboard. User data is saved in the browser: IndexedDB, with a localStorage fallback (PRD §2.2 and §10–12). P0, P1 and P2 are implemented. P1 added the 3D lab, battery banks, voltage drop, the rule registry, equipment profiles, day/night controls, PNG/SVG/PDF export, the PWA and IndexedDB. P2 added fault scenarios with field measurements, routed 3D cables, grid-tied/hybrid/generator systems, catalog-file import and a Filipino UI.

## Frontend commands (run in `frontend/`)

```bash
npm run dev       # Vite dev server
npm run build     # tsc -b && vite build (type-check + bundle + PWA service worker)
npx vite preview  # serve dist/ (the service worker and offline mode only work here, not in dev)
npm run lint      # oxlint
npm test          # vitest run (engine, storage, and the solvability of every lesson task and challenge)
npx vitest run src/storage/repository.test.ts   # one file;  add -t "name" for one test
npx shadcn@latest add <component>   # add shadcn/ui components into src/components/ui
```

## Frontend architecture

Vite + React 19 + TypeScript, Tailwind v4, shadcn/ui (`base-nova` style, built on **Base UI**, not Radix: triggers compose via the `render` prop, `Select` needs `items` for `SelectValue` to show labels, `Slider` takes array values), and Zustand. The UI is a port of the claude.ai/design files "Virtual Lab" (light) and "Virtual Lab v2 Dark".

- `src/engine/`: pure TS, with no React in it. `catalog.ts` holds component definitions, terminals, the ampacity table and the voltage-drop constants. Instance ids are UUIDs from `uid()`. Adding a spec key to the catalog is safe because `migrateProject()` (storage/migrations.ts) fills missing keys on load and import; bump the type's `ver` when you do. `geometry.ts` holds node/terminal layout and wire paths. Nodes rotate clockwise in 90° steps (`rot?: 0|90|180|270`, absent = 0): catalog `L` terminals sit on the left/top/right/bottom edge at 0/90/180/270, 90°/270° cards are wider and shorter (`nodeSize`), and `TerminalPoint` carries an outward `dx`/`dy` that `wirePath` routes from. Always size cards with `nodeSize`, not `NODE_W`. The 3D placement turns by the same angle (`rotY = -rot`). `validation.ts` holds the per-wire stages 1–4 (`checkWire`) and the system-level topology/ratings/protection/grounding rules (`validate`, which uses union-find over terminals). PV strings and **battery banks** (series strings in parallel, giving `BatteryBank`) are both found by `findStrings` between two nets. `sys.bank` and `sys.invBank` replace a single battery. The voltage drop (RAT-007) is computed after the systems are known, because it needs the circuit voltage. `simulation.ts` holds `compute` for instantaneous measurements and `step` for one clock tick plus event-log entries. `sample-project.ts` is the seed system. `scenario.ts` has `simulateDays`, a deterministic headless multi-day run used for grading and the PDF. `rules.ts` is the rule registry (PRD §7.3 metadata). Every rule id used in `validation.ts` must be registered, and a test enforces it. `profiles.ts` holds the equipment profiles; they are **example data** with illustrative values, as the user chose, so never present them as real manufacturer specs. `layout3d.ts` is the pure 2D→3D placement, terminal positions and sun direction.
- Current flow animation: `engine/flows.ts` `wireFlows()` derives the current in every wire from one `compute()` result. Components inject current at their terminals, internal bonds (busbars, closed breaker, meter, active ATS side) merge terminals, and wire currents are spanning-tree sums rooted at the least certain source (battery, hybrid, inverter). It's display-only and never feeds validation. `canvas.tsx` `FlowLayer` draws `.flow-dots` (CSS in `index.css`, `--flow` vars, off under `prefers-reduced-motion`), paused when the simulation is paused. Toggle with the canvas ⚡ Flow button or the `showFlow` setting.
- Convenience outlet (`outlet`, rule set 1.3.0): a duplex outlet whose L in and two sockets are one conductor (catalog `bus`). Validation walks the line conductor from each load along wires and through outlets to a board circuit output (L1/L2): that gives `sys.boardOf` (which RCD protects the load), `sys.outletsOf` and `sys.outletBoard`. Rules RAT-011 (outlet overloaded), GND-003 (outlet PE not earthed) and PRT-004 (outlet not on a board circuit). `solveAc` reports `outletsLive`. Tests are in `engine/outlet.test.ts`.
- P2 engine modules: `faults.ts` (injectable faults saved on the project as `faults`; challenge faults can be `hidden` and are found through symptoms), `measure.ts` (multimeter/clamp/insulation readings per node, shown in the inspector), `ac.ts` (`solveAc`: AC islands built from boards, net meters and ATS position; grid, generator, grid-tied and hybrid inverters; anti-islanding; generator auto-start), `schedule.ts`, and `catalog-import.ts` (zod-validated `solarsketch-catalog` JSON from real datasheets; imported profiles reach `profilesFor` through `setUserProfiles` and are stored in the `catalogs` KV key). Never ship invented brand data: built-in real devices come only from `docs/device-datasheets.md`, and users import their own datasheet values. Real (non-example) profiles are their own items in the library's **Real devices** tab (`deviceProfiles`, `makeDeviceNode`; the drag payload is `type|profileId`). A placed device keeps `node.profile` while its specs match; profile `settings` keys (installer settings such as battery reserve) can change without dropping the profile. Show device names with `nodeTitle(node, short?)`; engine messages keep the catalog name. Product photos live in `public/devices/<profile-id>.jpg` (≤480 px JPEG) and are registered in `engine/device-images.ts` with their source page, `official` and `match` (`exact`/`series`); the inspector credits the source. They are manufacturer-copyrighted, so get permission before a public release. Generic catalog components have Wikimedia Commons photos in `public/components/<type>.jpg`, registered in `engine/component-images.ts` with author, licence and file page (CC0, CC BY, CC BY-SA or public domain only). Anywhere a full photo is shown, render `ComponentCredit` beside it, since CC BY/BY-SA require credit. The grounding rod and water pump have no photo and fall back to the code badge; the DC breaker photo shows DC-rated panel-mount breakers from a PV combiner box, since Commons has no DC DIN-rail MCB. `layout3d.routeCable` gives orthogonal routes through floor trunking or the ceiling tray.
- `src/store/lab-store.ts`: a single Zustand store for the project, selection, view, undo/redo (JSON snapshots), simulation state and every canvas interaction (drag, pan, box select, wiring). Mouse and keyboard wiring share `pick()`/`connect()`. Simulation controls: `runToggle` (Start/Pause/Resume; after Stop it starts a new run), `stop` (halt, keep readings), `reset` (clear time, energy and log). The tick length is `tickMinutes(settings.simStep, speed)`: the time step setting (1/2/5/10/15 min, Settings and toolbar) times the ×1/×4/×12 speed. Transient pointer state (`drag`, `clip`, the viewport element) is kept in module variables so it doesn't trigger renders. `useValidation()` returns `validateCached(nodes, wires)`, which is memoised on array identity so every panel shares one validation run.
- `src/storage/`: the **only** code that touches browser storage. `backend.ts` has two backends with the same interface: IndexedDB (`solarsketch` DB, with a `projects` store and a `kv` store for meta, progress and challenges) and localStorage (the fallback). `repository.ts` is **async**: call `initStorage()` once (bootstrap does this), and it migrates any old localStorage data into IndexedDB. Writes are serialised through a queue, and every write can throw `StorageFullError`. Settings (theme, grid, panels) stay **synchronous** in localStorage under `solarsketch:settings`, because the pre-paint theme script reads them. Cross-tab change notices use a BroadcastChannel, or a `storage` event on `solarsketch:signal` where BroadcastChannel is missing. `schema.ts` holds the zod schemas and `STORAGE_SCHEMA_VERSION` (2). `migrations.ts` upgrades old documents step by step (`MIGRATIONS[v]` turns v into v+1; v1→v2 turned node `flip` into `rot: 180`) and fills missing spec keys, so older projects load instead of being reported corrupted: **a schema bump needs a migration step and a test**. Failed writes go through `store/storage-toast.ts` (`notifyStorageFull` offers Export project and My Projects; progress writes report there too). `parseImport` treats files as untrusted and assigns a new id. Tests use `fake-indexeddb/auto`.
- Persistence flow: `main.tsx` awaits `bootstrap()` (in `store/persistence.ts`) before the first render, which opens the last project, then the newest, then a saved sample. `startAutosave()` debounces `persist()` (800 ms) whenever nodes, wires, clear, speed, name or task change, and flushes when the page is hidden. `persist()` is async, and it marks the project saved only if nothing changed while the write was in flight. `watchOtherTabs()` warns about edits from other tabs. `store/project-actions.ts` (`openProject`, `newProject`, `startTask`) flushes the open project before switching. Before deleting or wiping the open project, set `saved: true` so autosave does not recreate it.
- `src/content/`: `lessons.ts` holds the lesson text and knowledge checks. `tasks.ts` holds the lesson practice tasks and challenges: a starter project, engine-evaluated `criteria` (`deferred` ones need the multi-day run), `allowed` components, prerequisites, a diagnosis question and `score()`. `tasks.test.ts` keeps a reference solution for every task, so **adding a task means adding its solution there**. A project carries `task: {kind, id}`, which `components/lab/task-bar.tsx` renders above the canvas.
- `src/store/progress-store.ts` is the reactive mirror of lesson progress and challenge attempts.
- Onboarding: `components/app/onboarding.tsx` is a first-run dialog (rendered in `App.tsx` outside the language-keyed shell, so switching language keeps the answers). It requires accepting the on-device-storage and educational-use notice, then asks for a name, expertise, purpose and goals, and suggests a start through `content/profile.ts` `recommend()`. Answers are a `Profile` (`storage/schema.ts`) in the `profile` KV key, mirrored by `store/profile-store.ts`; the dialog shows while `profile` is null. Settings edits the profile, and Run setup again (or Delete everything) clears it. Leaving the lab from onboarding saves the project and uses `navigateUnguarded`.
- `src/lib/router.ts` is a tiny hash router (`#/lab`, `#/learn/:id`, `#/challenges/:id`, `#/projects`, `#/progress`, `#/settings`, `#/components` and `#/components/:type`, which scrolls to and highlights that card; link lesson hardware references there). An empty or unknown hash is the Virtual Lab (PRD §2.1: the app opens on the lab, with the project `bootstrap()` loaded). Main nav (`components/lab/top-bar.tsx`, PRD order): Learn, Virtual Lab, Component Library, My Projects, Challenges, Progress, plus the Settings gear. The lab renders full-screen with its own `LabHeader` (`components/lab/lab-header.tsx`); `store/project-actions.ts` (new, open, template, task) also opens it. `LabHeader` registers `setLeaveGuard` (any hash that `parseHash` maps to the lab is allowed), so Exit (to My Projects, or back to the task's lesson/challenge), links and browser Back all show the exit confirmation, which saves before leaving and offers "Exit without saving" if the save fails; use `navigateUnguarded` after a confirmed exit. `App.tsx` is the shell: TopBar (hidden on the lab), the storage-unavailable banner, the current page and the sonner `Toaster`. Content pages use `components/app/page.tsx` (`Page`, `PageSection`, `RowList`, `Notice`, `Chip`) and the button classes in `components/app/styles.ts`.
- `src/hooks/use-lab-runtime.ts`: window mouse/keyboard handlers and the 220 ms simulation tick. Canvas keyboard use (PRD §14): nodes are focusable (`data-node-id`, Tab), Enter/Space select, arrows nudge (Shift = 50), R rotates, W on a focused node opens its terminal picker (`TerminalPicker` in canvas.tsx), Esc cancels, Space+drag pans; drag on empty canvas box-selects. The shortcut list lives in the canvas legend (`SHORTCUTS`). The tick runs only on the lab page, and leaving the lab pauses the simulation.
- `src/components/lab/*`: the panels (top bar, toolbar, library, canvas, console, inspector, status bar). The canvas is a custom HTML/SVG world transform rather than React Flow, so it can match the design exactly.
- `src/components/lab3d/lab-3d.tsx`: the 3D lab, built with React Three Fiber and drei. It is `lazy()`-loaded in `pages/virtual-lab.tsx` when `viewMode === '3d'`. It renders the same store state, selection and live `compute()` results; wiring is still edited in 2D. Labels are a DOM overlay positioned by `LabelProjector` each frame. **Do not use drei `<Html>`**: it throws `removeChild` errors when the Canvas unmounts. Switching environment moves the camera through `CameraRig`; never re-key the Canvas. `WalkControls` moves the camera and the orbit target together with WASD/arrow keys and Q/E for down/up (Shift runs); `use-lab-runtime.ts` ignores W/A/S/D/Q/E in 3D so they don't switch tools.
- `src/export/`: `diagram.ts` builds a standalone SVG from project data (fixed light palette) and rasterises it to PNG. `report.ts` (jsPDF + autotable, loaded with a dynamic import) builds the PDF report. The built-in PDF fonts are WinAnsi, so pass text through `pdfText()`.
- i18n: `src/i18n/` (`t()` for module-level use, `useT()` in components, `useLangStore`). English source strings are the keys and missing keys fall back to English; placeholders are `{name}` and `i18n.test.ts` checks they survive translation. The language is saved in settings (`lang`), and `App` re-keys the shell on change. Only UI chrome is translated (`fil.ts`). Lesson text, rule explanations and engine messages stay English until a qualified reviewer checks technical translations. Wrap new UI strings in `t()` and add the Filipino entry; don't name local variables `t`.
- PWA: `vite-plugin-pwa` is set up in `vite.config.ts` (it precaches the build, including the fonts). Fonts are self-hosted: `src/fonts.css` declares Google Sans (latin, latin-ext, greek, symbols subsets) from `@fontsource-variable/google-sans`; the app makes no third-party requests.
- CSP (PRD §14): `cspPlugin` in `vite.config.ts` runs on **build only** (dev needs inline React Refresh and HMR). It hashes every inline `<script>` left in the built `index.html` (the pre-paint theme script), injects a `Content-Security-Policy` meta tag, and writes `dist/_headers` (Netlify/Cloudflare Pages) with the same policy plus `frame-ancestors`, nosniff, referrer and permissions headers. Editing the theme script needs nothing else; adding a third-party origin means adding it to the policy. Check with `npm run build && npx vite preview`. `components/app/pwa-prompt.tsx` shows the "ready offline" and "update available" toasts.
- Splash and loader: `index.html` has a static `#splash` (plain HTML and inline CSS, so it shows before JS loads; it hardcodes the theme background colours) that `main.tsx` fades out after the first render, at least `SPLASH_MIN_MS` (1.2 s) from page load. After that, `withLoader()` in `store/loader-store.ts` shows `components/app/sun-loader.tsx` (the animated `SunMark`). Opening a project uses it for at least 700 ms (`store/project-actions.ts`), and every page change uses it for 450 ms (`usePageLoader` in `App.tsx`, skipped while a project-opening loader is already up).
- **Two themes, one component tree.** Light (`:root`) is the design "Virtual Lab" and dark (`.dark`) is "Virtual Lab v2 Dark". All differences live in CSS variables in `src/index.css`. Both themes deliberately use subtle 1px panel borders (`--bw`), a 20px toolbar divider, a 2px nav underline and a filled tool hover. The light design originally had 2px ink borders, but the user asked for dark-mode-style borders, so don't reintroduce them. Remaining differences are colour plus bold weight (`--fw-strong`: 800 in light, 700 in dark). Use the `edge`/`edge-{t,r,b,l}` and `font-strong` utilities rather than `border border-border` or `font-bold`. On shadcn controls use `border-(length:--bw) border-border`. Terminal and wire colours are CSS vars in `components/lab/colors.ts`, and SVG strokes take them through `style`, not attributes. `useTheme()` toggles the `.dark` class and saves the choice to `solarsketch:settings`; an inline script in `index.html` reads that key before first paint. `--radius` is 0, so shadcn components render square.

## What the product is

A frontend-only web app: a virtual lab for learning solar PV installation, targeting the Philippines (learners, technicians, students, TESDA/training institutions). Users drag hardware components onto a 2D canvas, wire terminals together, and run an electrical simulation that validates connections and models generation, battery state of charge, inverter conversion and loads. A 3D lab visualizes the same project.

## Stack (PRD §10.1)

- React + TypeScript (Vite), shadcn/ui + Tailwind, Zustand. The 2D canvas is custom HTML/SVG; the 3D lab uses Three.js, React Three Fiber and drei. Other libraries: zod, idb, jsPDF and vite-plugin-pwa.
- Persistence is IndexedDB (localStorage fallback) plus `.solarsketch.json` file export/import.
- Deployed as a static site. There is no server, database or auth. A backend (accounts, instructor portal, sync, subscriptions) is an explicitly deferred future phase. Don't add one or design for it unless asked.

## Architectural rules that span modules

These come from the PRD and constrain how code should be structured:

1. **One shared electrical engine.** The 2D canvas and the 3D renderer both consume the same project model and the same graph/validation/simulation engine. The 3D layer never computes electrical behavior itself.
2. **Everything runs in the browser.** Validation, simulation, scoring and persistence are all local TypeScript, and the app should work offline once loaded. Catalog, rules, lessons and challenges ship as versioned static data.
3. **Independent modules:** electrical graph, validation engine, simulation engine, component registry, and safety-rule registry are separate. Keep them separate from UI code so the simulator can be upgraded without touching the app.
4. **Electrical graph model:** nodes are terminals and junctions, edges are wires, and components define behavior and constraints between their own terminals. A visual connection is not a valid connection until it passes validation.
5. **Six-stage connection validation**, in order: terminal → AC/DC domain → polarity → ratings → topology → protection. Every failure returns a human-readable explanation, not just a code.
6. **Deterministic and rule-based.** Never use an LLM to decide electrical validity. Identical inputs plus the same rule version must give identical results.
7. **Safety rules are data.** Each rule carries: id, description, severity (Critical / Warning / Information), applicable component, detection conditions, explanation, corrective action, reference source, and version.
8. **Component catalog vs. instances.** Catalog definitions (`ComponentDefinition` in PRD §4.2: terminals, specifications with units, capabilities, constraints, assets, version) are kept separate from project instances. Saved projects must keep the component spec version they were built with. Don't assume components in the same category share ratings.

## Local data conventions (PRD §11–12)

- All storage access goes through one storage repository module (`listProjects`, `loadProject`, `saveProject`, `exportProject`, `importProject`, and so on). UI code never touches `localStorage` directly.
- Keys use the `solarsketch:` prefix. Each project lives under its own key, `solarsketch:project:{id}`, with a summary index in `solarsketch:projects:index`. Progress, challenge attempts and settings each have their own key.
- A project is a `ProjectDocument` with `schemaVersion`, a UUID, timestamps, rule-set and catalog versions, nodes (with their own spec values and spec version) and wires. A `.solarsketch.json` export is that same document. Migrate on load by `schemaVersion`.
- Never persist simulation time-series or event logs; they are regenerated. localStorage holds about 5 MB, so handle `QuotaExceededError`, corrupted entries and unavailable storage without losing the open project.
- Treat imported files as untrusted: validate the schema and assign new ids.

## Domain and safety constraints

- The product is educational only. Never produce UI copy or logic that implies a simulation certifies a real installation, PEC compliance, or professional approval.
- The MVP PV model is the simplified formula `P_PV = P_STC × (G/1000) × f`. It must state its assumptions.
- Wire colors (DC+ red, DC− black, ground green/yellow) are visual conventions only. Show errors in a way that doesn't rely on color alone.
- Canvas performance: wire interaction must feel immediate, and canvas updates must not trigger app-wide re-renders.

## Scope status

- **P0 (done):** no-login entry into the Virtual Lab, component library and properties panel, 2D wiring, the validation stages, series/parallel, solar/battery/inverter/load models, the simulation console, save/autosave/load, My Projects with `.solarsketch.json` export/import, beginner lessons, troubleshooting challenges, and safety warnings.
- **P1 (done):** 3D lab (training laboratory and residential rooftop) with 3D inspection, day/night controls, battery banks, example equipment profiles, cable length and voltage drop, the expanded rule registry, PNG/SVG/PDF export, PWA offline mode, and IndexedDB.
- **P2 (done):** advanced fault scenarios (troubleshooting challenges with hidden faults), advanced 3D cable routing, grid-tied/hybrid/generator simulation with templates, manufacturer catalog import (user-supplied datasheet JSON), and internationalization (English/Filipino UI).
- **PRD gap pass (done):** the remaining PRD items beyond the P0–P2 lists:
  - **Catalog metadata:** `engine/catalog-meta.ts` holds desc, maker, constraints, symbol, model3d and configs for every type, and the type checker requires an entry for each new type.
  - **Inline devices:** MC4, Y-branch, combiner, fuse, isolator, SPDs, MCB/MCCB/RCCB, AC disconnect, busbars, DC/AC meters and the microinverter are checked in `engine/inline.ts`. `engine/runtime.ts` re-validates when fault-opened devices change and produces the meter readings. Every rule id used in `inline.ts` must be registered (`components.test.ts`).
  - **Battery and PV types:** battery chemistries are in `engine/battery-chem.ts`. Use `BATTERY_TYPES`/`isBattery` and `PV_TYPES`/`isPv`, never `type === 'bat'` or `'pv'`.
  - **Engine model:** PV temperature and orientation (f = 0.88), load surge and priority shedding, inverter frequency, LVD and thermal trip, the rule `fix` field, findings ordered by stage, SHC-001, PRT-005/006 and BND-001 bonding (PE terminals on PV, controllers and lithium batteries).
  - **Lessons:** levels 1–5 with figures, calculators, hardware references and animated walkthroughs, built from `src/components/learn/`.
  - **Storage:** `storage/migrations.ts` holds the per-version migrations (schema v2: node `rot` replaces `flip`).
  - **Production build:** a CSP and `dist/_headers`, and self-hosted fonts.
- **Future (needs a backend, not planned):** accounts, instructor portal, sync, share links and subscriptions.
